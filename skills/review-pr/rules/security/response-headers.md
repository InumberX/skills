# セキュリティ観点: レスポンスヘッダ

対象: レスポンスヘッダを設定している箇所。静的ホスティングの `_headers`、フレームワークのヘッダ設定、Worker やサーバー側で付与する処理のいずれも含む。

組み込みの `/security-review` は「ハードニング不足は報告しない。具体的な脆弱性のみ」という方針で、**ヘッダの後退を一切扱わない**。ここは本スキルが引き取る領域なので、除外を理由に読み飛ばさない。

扱うのは**既にあるヘッダを弱める変更**である。「ヘッダが1つも無い」はリポジトリ全体の棚卸しに属し、差分を起点とする本スキルのスコープ外になる。

## 1. CSP を緩める変更は、緩めた理由とセットで見る

`Content-Security-Policy` は一度緩めると気づかれない。動かないものを動かすために足されることが多く、**目的は達成されるので差し戻す動機が生まれない**。

差分での見つけ方: 次が追加されていたら、何を動かすためかを確認する。代替手段（nonce、hash、外部ファイル化）で済まないかを併せて見る。

- `'unsafe-inline'` / `'unsafe-eval'`
- ワイルドカード（`*`、`https:` のようなスキーム全体の許可）
- ディレクティブそのものの削除（`object-src`、`base-uri`、`form-action` は消しても表示は壊れないため落ちやすい）
- nonce や hash の方式をやめて `'unsafe-inline'` へ戻す変更

## 2. `frame-ancestors` を外すと埋め込みを止められなくなる

`frame-ancestors`（および `X-Frame-Options`）が無いと、他サイトが iframe で埋め込める。クリックジャッキングの前提条件になる。

差分での見つけ方: プレビュー機能や埋め込み対応のために外していないか。特定の埋め込み元を許可したいなら、削除ではなくオリジンの列挙にする。

## 3. 適用パスを変えるとヘッダの掛かる範囲が変わる

`_headers` のようなパス単位の設定では、**パターンを書き換えた結果ヘッダが掛からなくなるパスが生まれる**ことがある。設定を追加したつもりで既存の指定を上書きしている場合もある。

差分での見つけ方: パス指定が変更されたら、変更前に掛かっていて変更後に掛からなくなるパスが無いかを確認する。ヘッダを複数箇所（静的ホスティング側とアプリケーション側）で設定している場合は、**どちらが最終的に勝つか**も確認する。

## 4. ヘッダの設定箇所が増えたら、既存と衝突していないか見る

同じヘッダを複数の層で設定すると、後から追加した側が意図せず既存の値を置き換える。特に CSP は**後勝ちではなく両方が適用され、両方を満たす必要がある**ため、片方が厳しいと動かなくなり、その解決として緩い方へ寄せられやすい。

差分での見つけ方: 新しくヘッダを設定する箇所が増えたら、同じヘッダを設定している既存箇所を探す。
