# セキュリティ観点: Cloudflare Workers

対象: Wrangler 4 系の設定ファイル（`wrangler.jsonc` / `wrangler.json` / `wrangler.toml`）と Worker のエントリポイント。3 系以前は未検証（JSON 形式の設定は 3.91 以降。`run_worker_first` の導入時期は未確認なので、古い Wrangler では項目1が当てはまらない可能性がある）。

`boundary.md` の server / client 境界とは別軸で、**プラットフォーム設定によるゲートの無効化**を扱う。内容はほぼ重ならないが、認可をどこに置くかについては `boundary.md` の項目4と併せて読む。

Worker で認証・認可のゲートを実装している場合、**ゲートのコードを一切変えなくても、設定1行の変更でゲートが無効化される**。設定ファイルが差分に含まれていたら必ず確認する。

## 1. `assets.run_worker_first` を外すと静的アセットがゲートを迂回する

静的アセットのバインディングは、既定では**マッチするファイルを Worker より先に返す**。Worker で認証ゲートを実装していても、`run_worker_first` が無い/`false` だと JS・CSS・画像・生成済み HTML が認証なしで配布される。

**この値は真偽値だけでなく URL パターンの配列も取る。** 配列にすると、パターンに一致しないパスは Worker を経由しない。

```jsonc
// サイト全体をゲートで守る場合
"run_worker_first": true

// パターン指定。ここに含まれないパスは Worker を通らず配信される
"run_worker_first": ["/api/*", "!/api/docs/*"]
```

差分での見つけ方: `assets` ブロックから `run_worker_first` が消えた、`false` になった、新規に `assets` を追加したのに指定していない、のいずれか。**`true` から配列へ変わった差分は特に注意する** — 一見「設定を細かくしただけ」に見えるが、保護対象がパターンの外に出ていればその時点でゲートが外れる。配列の場合は、守るべきパスがすべて含まれているか（否定パターン `!` で除外されていないか）まで確認する。

## 2. `workers_dev` を有効にすると別経路で公開される

`workers_dev: true` にすると `*.workers.dev` のサブドメインからも到達できるようになる。カスタムドメイン側に WAF ルールやアクセス制限を掛けている場合、**その経路だけが素通しになる**。カスタムドメインのみで運用する Worker では `false` を維持する。

差分での見つけ方: `workers_dev` が `true` へ変わった、または新規 Worker で指定が無い（既定で公開される）。

## 3. 機密を `vars` に書かない

`vars` の値は設定ファイルに平文で書かれ、**リポジトリにコミットされダッシュボードからも見える**。トークン・パスワード・API キーは `wrangler secret put <NAME>` で登録する。

差分での見つけ方: `vars` に機密らしき値が追加されていないか。公開してよい設定値（ユーザー名・TTL 秒数・機能フラグ）は `vars` で問題ない。

補足: 環境を分けている場合、シークレットは**環境ごとに登録が必要**（`--env=<name>`）。片方の環境だけ未登録になると、その環境でゲートの設定が欠けた状態になる。設定変更で環境を追加した差分では、シークレット登録の要否も確認する。

## 4. 資格情報の検証は「部分設定で fail closed」「定数時間比較」

環境変数は未設定だと `undefined` になるため、素直に書くと**設定漏れがゲートの無効化として現れる**。

```ts
// Bad: 片方だけ設定されている / 両方未設定のとき、認証なしで通過する
if (!user || !pass) return handler(request)

// Good: 片方だけ設定されているのは設定ミス。開けずに落とす
if (Boolean(user) !== Boolean(pass)) return new Response(null, { status: 503 })
```

「未設定なら認証を無効化する」仕様を意図的に採る場合でも、**両方未設定のときだけ**に限定する。片方だけ設定された状態を通過させてはいけない。

資格情報の比較に `===` を使うと、一致する接頭辞の長さによって処理時間が変わる。ハッシュ化してから固定長で比較する、または既存の定数時間比較ユーティリティを使う。ユーザー名とパスワードの検証を直列に書くと、ユーザー名が違う場合だけ早く返るため同様の情報が漏れる（並列に評価する）。

差分での見つけ方: 資格情報の比較・早期 return の追加。既存の定数時間比較を `===` に置き換えていないか。

## 5. キャッシュはゲートの後ろに置き、キーに応答を変える要素をすべて含める

Cache API を使う Worker では順序が重要になる。**認証を通過した後の応答をキャッシュし、次のリクエストで認証前にそれを返すと、認証が実質無効になる**。ゲート → キャッシュ参照 → ハンドラの順にする。

キャッシュキーには「応答を変える入力」をすべて含め、逆に**含めない入力は応答に影響してはいけない**。クエリパラメータを追加したのにキーの許可リストを更新しないと、異なる応答が同じキーに衝突する（別の利用者向けの応答が返る）。

差分での見つけ方: クエリパラメータ・ヘッダ・パス要素の追加時に、キャッシュキーの生成側も同じ差分で更新されているか。変更ファイルがハンドラ側だけでも、**キー生成の定義箇所まで確認する**。

## 6. `assets.not_found_handling` の変更はフォールスルー経路を変える

この値は、アセットが見つからないときにバインディングが何を返すかを決める。`"single-page-application"` は未マッチのパスに対して 200 でアプリシェルを返し、`"none"` は 404 を返す。**Worker 側が「404 が返ってきたら自前で処理する」設計になっている場合、この値の変更でその分岐に到達しなくなる**。

差分での見つけ方: `not_found_handling` の変更時に、Worker のフォールスルー処理（自前の 404、言語別出し分け、ゲート後の処理）が前提を保てているか。

## 7. ログに資格情報を出さない

`observability` を有効にしている Worker では、リクエストヘッダをそのまま出力すると `Authorization` ヘッダや Cookie がログに残る。設定ミスの警告を出す場合も、値ではなく**どのキーが欠けているか**だけを出す。
