# セキュリティ観点: Next.js

対象: Next.js 15 / 16 の App Router。Pages Router と 14 以前は未検証。

## 1. Server Action は公開エンドポイント

`'use server'` を付けた関数にはフレームワークが ID を割り当て、**ブラウザから直接呼び出せる**。呼び出し元のコンポーネントを条件付きで描画していても、関数そのものは到達可能なため認可にならない。**認可と入力検証は Server Action の内部に置く。**

差分での見つけ方: `'use server'` の追加時に、その関数がセッション・権限を自分で検証しているか。フォームを出し分けているだけになっていないか。Route Handler（`route.ts`）も同様に公開エンドポイントとして扱う。

## 2. `proxy.ts` / `middleware.ts` に認可を集約しない

Next.js 16 で `middleware.ts` は `proxy.ts` にリネームされ（エクスポート名も `middleware` → `proxy`）、位置付けが「ルーティングと粗いチェックの層」であることが明確化された。**実際の認証・認可は Server Component / Server Action / Route Handler 側で行う**のが公式の指針。

理由は名前だけの問題ではない。過去に `x-middleware-subrequest` ヘッダでミドルウェアを迂回できる脆弱性（CVE-2025-29927）があり、ここに認可を集約していると全経路が同時に破られる。

差分での見つけ方: `proxy.ts` / `middleware.ts` に認可ロジックが追加され、保護対象側には何も足されていない差分。既存の `middleware.ts` を残す判断をしている場合、その理由がプロジェクト側に記録されているかも確認する（実行環境の制約で意図的に残していることがある）。

## 3. `NEXT_PUBLIC_` はバンドルへ埋め込まれる

`NEXT_PUBLIC_` を付けた環境変数はビルド時に値が展開され、**公開されるバンドルに文字列として含まれる**。サーバー専用の環境変数と記述の見た目が接頭辞しか違わないため、機密を移してしまっても差分上は目立たない。

差分での見つけ方: `NEXT_PUBLIC_` 付きの参照が追加されたら、その値が公開されてよいか。既存の変数に接頭辞が足されていないか。

## 4. Server Component から Client Component へ渡す props はクライアントへ届く

Server Component で取得したデータを `'use client'` のコンポーネントへ渡すと、シリアライズされて RSC ペイロードに載る。**画面に描画していないフィールドも含めて配布される。**

差分での見つけ方: 境界をまたぐ props にレコードを丸ごと渡していないか。必要なフィールドだけに絞ってから渡す。

## 5. キャッシュに閲覧者ごとに変わる応答を入れない

`'use cache'`、`revalidate`、フェッチ単位のキャッシュなどでキャッシュされた結果は、**キーが同じなら別の閲覧者にも返る**。認証状態やユーザー ID によって内容が変わるデータをキーへ含めずにキャッシュすると、他人向けの応答が配られる。

差分での見つけ方: キャッシュ指定が追加された関数・フェッチが、閲覧者に依存しない内容だけを返しているか。依存するならキーに閲覧者を識別する要素が含まれているか。
