# セキュリティ観点: GitHub Actions

対象: `.github/workflows/` のワークフロー定義。GitHub 側の仕様（トリガーごとのトークン権限、fork PR の扱い）に依存するため、挙動が変わった場合は前提から確認する。

`boundary.md` の server / client 境界とは別軸で、**ワークフローに入る信頼できない入力**を扱う。内容は重ならない。

組み込みの `/security-review` は GitHub Actions の指摘をほぼ除外する（「実際には悪用できないものが大半」という前提で、明確な攻撃経路がある場合のみ報告する方針）。**ここは本スキルが引き取る領域**なので、除外を理由に読み飛ばさない。

## 先にリポジトリの公開範囲を確認する

同じ注入でも、公開範囲によって**到達できる人**が変わる。トリガーより先に確認する。

| 公開範囲 | fork からの PR | ブランチ名や PR タイトルを決められる人 |
| --- | --- | --- |
| 公開 | 誰でも開ける | **任意の GitHub ユーザー** |
| 非公開 | 実質発生しない | 書き込み権限を持つ協力者のみ |

非公開リポジトリでは、注入できる人はすでにコードを直接 push できるため、**追加されるリスクは小さい**。ただし修正しない理由にはならない。協力者ごとに権限が異なる場合や、後からリポジトリを公開した場合に、そのまま危険度が上がる。

## 先にトリガーを確認する

同じ注入でも、トリガーによって被害の範囲が反転する。**ワークフロー名やジョブの内容より先に `on:` を読む。**

| トリガー | 実行コンテキスト | 注入が成立したときの被害 |
| --- | --- | --- |
| `push` / `schedule` / `workflow_dispatch` | シークレットあり・トークンは設定どおりの権限 | リポジトリ侵害。シークレットの流出 |
| `pull_request_target` / `issue_comment` / `issues` | 同上（**fork の PR でもシークレットが渡る**） | 同上。最も危険な組み合わせ |
| `pull_request`（同一リポジトリのブランチ） | シークレットあり | 同上 |
| `pull_request`（fork から） | **シークレットは渡らず、トークンは読み取り専用** | ランナー上の任意コード実行にとどまる |

fork からの `pull_request` は被害が限定されるが、**注入自体は成立する**ので指摘対象から外さない。初回コントリビューターの実行に承認を要する既定設定は緩和要因であって、修正しない理由にはならない。

## 1. `${{ }}` を `run:` へ直接展開しない

`${{ }}` の展開は**シェルが起動する前のテキスト置換**で行われる。値がスクリプトの一部として貼り込まれるため、信頼できない入力にシェルのメタ文字が含まれると、そのままコマンドとして実行される。

```yaml
# Bad: ブランチ名は PR 作成者が自由に決められる
- run: |
    branch_type=$(echo ${{ github.head_ref }} | cut -d "/" -f1)

# Good: env 経由にする。シェル変数の参照になり、テキスト置換が起きない
- env:
    HEAD_REF: ${{ github.head_ref }}
  run: |
    branch_type=${HEAD_REF%%/*}
```

**信頼できない入力の例**: ブランチ名・タグ名（`github.head_ref`、`github.ref_name`）、PR やイシューのタイトル・本文、コメント本文、コミットメッセージ、レビュー本文、そして**これらを材料に GitHub の API が生成した文字列**（リリースノートは PR タイトルを含む）。

引用符で囲んでも防げない。二重引用符の中でも `` ` `` と `$( )` はコマンド置換として評価される。ダブルクォートだけを除去する処理を挟んでも同じ理由で不十分。

差分での見つけ方: `run:` ブロックの中に `${{` があったら、その値の出所を辿る。リポジトリ側が決めた固定値なら問題ない。外部から与えられる余地があるなら `env` 経由へ移す。**注入経路が現在は不発でも指摘する** — 廃止記法などで値が空になっているだけの場合、移行や修正のタイミングで生きる。

## 2. `permissions` を最小化する

ジョブに `permissions` が無いと、`GITHUB_TOKEN` はリポジトリ設定の既定値を受け取る。既定が書き込みのリポジトリでは、検査だけのジョブでも書き込み可能なトークンを持つ。

ワークフローはサードパーティのアクションとパッケージの依存ツリーを実行する。**そこに不要な権限のトークンを置かない**のが目的で、これは設定1行で確定できる。

```yaml
jobs:
  test:
    permissions:
      contents: read
```

差分での見つけ方: ジョブが追加されたのに `permissions` が無い。既存ジョブに書き込みを要する処理（リリース作成、PR 作成、ラベル付与）が足されたのに権限の記述が変わっていない。

## 3. `pull_request_target` で PR のコードを実行しない

`pull_request_target` は**ベースブランチの定義で、シークレットを持って**動く。ここで PR 側の ref を `checkout` して、その中身をビルド・テスト・スクリプト実行すると、**fork から送られた任意のコードがシークレット付きで動く**。

差分での見つけ方: `pull_request_target` が追加されたら、`actions/checkout` の `ref` を必ず確認する。`github.event.pull_request.head.sha` などを指定していれば危険。PR のコードを動かす必要があるなら `pull_request` を使う。

## 4. サードパーティのアクションはバージョンを固定する

`uses:` の参照先が可変（`@main`、メジャータグのみ）だと、上流の更新がそのままワークフローの実行内容の変更になる。供給元が侵害された場合も同じ経路で影響を受ける。

差分での見つけ方: `uses:` に新しいアクションが追加されたとき、参照が固定されているか。同一リポジトリ内で `@v4` と `@v2` のように世代が混在していないか（片方だけ更新が止まっている兆候）。
