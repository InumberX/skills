# レビューの進め方

指摘を書く前に、毎回読む。プロジェクトやフレームワークを問わず、指摘の根拠を確かにし、レビューの範囲を誤らないためのルールである。観点本文（命名・スタイル・セキュリティ）とは別に適用する。

## 指摘の根拠

### ライブラリの挙動を根拠にするとき

外部ライブラリの挙動を根拠に指摘する前に、**プロジェクトが使っているバージョン**で実際の出力を 1 回取り、その出力とバージョン番号を指摘に添える。バージョンは lockfile で確かめる。

ライブラリの挙動はバージョンで変わる。記憶やドキュメントの最新版をもとに指摘すると、そのプロジェクトでは起きない問題を指摘したり、起きる問題を見逃したりする。出力を取れない場合は、指摘に「未検証」と書く。

### 同じ名前の関数が複数あるとき

同じ名前の関数やコンポーネントが複数のモジュールにある場合は、名前だけで同定しない。**ファイルパスと引数のシグネチャの両方**を差分と突き合わせてから指摘する。取り違えると、変更してはいけない側を変更させる指摘になる。

### PR に「実行できなかった」と書かれた検証

PR 本文に「この環境では実行できない」「未実行」と書かれた検証は、レビューする側の環境で実行できるなら実行し、結果を指摘に併記する。実行できない場合は、未検証のまま残っていることを指摘として挙げる。書き手とレビュアーのどちらも実行しないまま、マージされるのを防ぐ。

## 先に確かめること

### ユーザーからの入力を受け取る機能

問い合わせフォーム、投稿、アップロードなど、ユーザーからの入力を受け取る機能の PR では、コードを見る前に、次の 3 点が PR か紐づく Issue に書かれているかを確かめる。

- 受け取った後、誰が対応するか（運用の担当）
- 個人情報をどこに、いつまで保持するか
- 通知が誰に届くか

書かれていなければ、コードの指摘より先にそれを指摘する。この 3 点が決まっていないと、コードが正しくても運用できず、個人情報の扱いが宙に浮く。

### ライブラリを移行する PR

ライブラリやツールを別のものへ移行する PR では、差分を確かめた後に、`package.json` の scripts と設定ファイルを列挙し、移行前の仕組みに依存するものが残っていないかを 1 件ずつ確かめる。差分に現れないファイル（CI のワークフロー、エディタの設定、ドキュメントのコマンド例）に、移行前のコマンドや設定が残りやすい。

## レビューの範囲

- **レビューを頼まれたら、指摘を出すところで止める。** 修正まで頼まれていない限り、コードを書き換えない。どの指摘を採るかは書き手が決める
- 「この PR だけ」「このファイルだけ」と範囲を指定された場合は、範囲の外にある問題を指摘に混ぜない。気づいたものは、範囲外として最後に分けて挙げる

## 同じ指摘を繰り返したとき

同じ趣旨の指摘を、別の PR で 2 回以上したら、その方針をプロジェクトの `CLAUDE.md` / `AGENTS.md` か、プロジェクトの `review-pr/rules/` に追記することを提案する。指摘のたびに説明し直すより、規約として残した方が、書き手も次から守れる。`record-lesson` スキルがあれば、その手順に従う。
