# コード内コメント

差分で追加・変更されたコメントに対して、毎回適用する。言語やフレームワークに依存しない観点だけを置く。コメントの有無そのもの（関数ごとに書く、など）の規約は、各プロジェクトの `rules/` に任せる。

## 経緯はコメントではなく PR 本文に書く

コメントに書くのは、**今のコードがなぜこうなっているか**と、**挙動がどこから来るか**だけにする。「以前は〜だった」「〜のバグを直すために変えた」のような変更の経緯は、PR 本文かコミットメッセージに書く。

「何があって変えたか」という変更の物語は、今のコードを理解するのに要らない。しかもコードが次に変わったとき、経緯のコメントだけが直されずに残り、存在しない過去の実装を説明し続ける。PR 本文は差分と一緒に残るので、経緯を追いたい人はそこから辿れる。

一方、**なぜ別の案を採らないのか**は、今のコードの理由なので残してよい。読み手が「こう書けば簡単なのに」と考えて元に戻すのを防ぐためである。区別は、過去の出来事を語っているか、今の選択の理由を語っているかで付ける。

```ts
// Bad — 修正前の経緯（変更の物語）。PR 本文に書けば足りる
// 以前は ID 順で返していたため、後から取り込んだ過去の注文が先頭に来ていた。注文日順に変更した
```

```ts
// Good — 今の実装の理由（採らなかった案を含む）と、挙動の出どころだけ
// 過去の注文を後から取り込むことがあるので、ID ではなく注文日で並べる。
// 同じ注文日の並びは、呼び出し先のページング関数が ID を足して決めている
```

指摘するときは、コメントの代わりに PR 本文のどこへ移すかを添える。PR 本文に既に同じ説明があるなら、コメントを削る提案でよい。

## 条件を言い切るコメントは、コードの分岐と突き合わせる

「必ず」「〜しか」「〜すると〜になる」のように条件を言い切るコメントは、コードの分岐やデータの取得条件と突き合わせ、**その条件が成り立たない場合が無いか**を確かめる。成り立たない場合があるなら、「〜ことがある」と書くか、成り立つ条件を書き足すよう指摘する。

言い切りのコメントは、読み手が自分でコードを確かめない理由になる。実際には一部の場合にしか起きないことを「必ず起きる」と書くと、読み手は起きない場合への備えを外したり、起きない場合の不具合を探さなかったりする。

```ts
// Bad — 在庫を引き当てないのは、予約注文のときだけ。すべての注文で引き当てないように読める
// 注文を作っても、在庫は引き当てない
```

```ts
// Good — 成り立つ条件を書く
// 予約注文のときは、発売日まで在庫を引き当てない
```

突き合わせには、コメントが参照している関数やクエリの定義まで辿る。取得の条件が別のリポジトリ（API など）にある場合は、そこまで読んでから判断する。読めない場合は、指摘に「未検証」と書く。

## 用語は、コード上の実際の条件に合わせる

コメントの用語が、コードの条件より広い意味や別の意味に読めないかを確かめる。たとえば実際の条件が「販売中フラグが立っている」なのに「公開中の商品」と書くと、別の状態（ページの公開、検索への掲載など）と区別がつかない。同じ条件を指すコメントが複数あれば、用語を揃えるよう指摘する。
