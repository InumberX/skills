# コード内コメント

差分で追加・変更されたコメントに対して、毎回適用する。言語やフレームワークに依存しない観点だけを置く。コメントの有無そのもの（関数ごとに書く、など）の規約は、各プロジェクトの `rules/` に任せる。

## 経緯はコメントではなく PR 本文に書く

コメントに書くのは、**今のコードがなぜこうなっているか**と、**挙動がどこから来るか**だけにする。「以前は〜だった」「〜のバグを直すために変えた」のような変更の経緯は、PR 本文かコミットメッセージに書く。

経緯は、コードを読む人が今のコードを理解するのに要らない。しかもコードが次に変わったとき、経緯のコメントだけが直されずに残り、存在しない過去の実装を説明し続ける。PR 本文は差分と一緒に残るので、経緯を追いたい人はそこから辿れる。

```ts
// Bad — 修正前の経緯。PR 本文に書けば足りる
// 以前は ID 順で返していたため、遡って登録した月が先頭に来ていた。日付順に変更した
```

```ts
// Good — 今の実装の理由と、挙動の出どころだけ
// 月は遡って登録されることがあるので、ID ではなく日付で並べる。
// 同じ月の行の並びは、呼び出し先のページング関数が ID を足して決めている
```

指摘するときは、コメントの代わりに PR 本文のどこへ移すかを添える。PR 本文に既に同じ説明があるなら、コメントを削る提案でよい。

## 条件を言い切るコメントは、コードの分岐と突き合わせる

「必ず」「〜しか」「〜すると〜になる」のように条件を言い切るコメントは、コードの分岐やデータの取得条件と突き合わせ、**その条件が成り立たない場合が無いか**を確かめる。成り立たない場合があるなら、「〜ことがある」と書くか、成り立つ条件を書き足すよう指摘する。

言い切りのコメントは、読み手が自分でコードを確かめない理由になる。実際には一部の場合にしか起きないことを「必ず起きる」と書くと、読み手は起きない場合への備えを外したり、起きない場合の不具合を探さなかったりする。

```ts
// Bad — 相手側が読み込まれないのは、相手が特定の側に入っている場合だけ。常に欠けるように読める
// 相手が非公開だと、取得結果に相手の名前が入らない
```

```ts
// Good — 欠ける条件と、欠けることがあるという程度を正確に書く
// 取得結果のうち一方の側は公開中のものしか読み込まれず、相手の名前が欠けることがある
```

突き合わせには、コメントが参照している関数やクエリの定義まで辿る。取得の条件が別のリポジトリ（API など）にある場合は、そこまで読んでから判断する。読めない場合は、指摘に「未検証」と書く。

## 用語は、コード上の実際の条件に合わせる

コメントの用語が、コードの条件より広い意味や別の意味に読めないかを確かめる。たとえば実際の条件が「公開フラグが立っている」なのに「公開中のプロジェクト」と書くと、別の公開状態（ページの公開、ユーザーの公開など）と区別がつかない。同じ条件を指すコメントが複数あれば、用語を揃えるよう指摘する。
