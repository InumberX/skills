## コーディングのルール

### コメント

- コメントを書く前に、名前の変更や関数への切り出しでコードだけで分かるようにできないかを考える。コードを読めば分かることを言い換えたコメントは書かない。冗長なコメントは直し忘れて古くなり、今のコードと違う説明で読み手を誤らせるため。
- コードを変えたら、変えた関数・ブロックの中にあるコメントと、変えた関数・定数・変数の名前を挙げているコメント（名前で検索して探す）が、変更後のコードと合っているかを確かめ、合わないものは直すか削る。古いコメントは、コメントが無いより悪いため。
- コメントには、今のコードがなぜこうなっているか（採らなかった案を含む）と、挙動がどこから来るかだけを書き、「以前は〜だった」のような変更の経緯はコミットメッセージか PR 本文に書く。経緯のコメントは、コードが次に変わると存在しない実装を説明し続けるため。
- 「必ず」「〜しか」のように条件を言い切るコメントは、コードの分岐と突き合わせて、成り立たない場合が無いことを確かめてから書く。言い切りは、読み手が自分でコードを確かめない理由になるため。
