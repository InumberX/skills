# investigate-failure

失敗の原因を、**コードを直す前に**特定するスキル。CI の失敗、テストの失敗、特定の環境でしか起きない不具合、表示されないもの、数値のずれ、性能の低下を対象にする。

調査の手戻りは、ほとんどが「原因を推測してから確かめ始めた」ことで起きる。ジョブ名だけを見て原因を決める、古いコミットの CI 結果を最新の状態として報告する、ローカルの修正を本番のサーバーで確かめていた、1 回しか起きていないずれを報告する、などである。どれも、何がどこで失敗したかを先に確定すれば防げる。

## いつ発動するか

次のいずれかに該当する場合に使う:

- 「CI が落ちた」「テストが通らない」と言われた
- 「動かない」「表示されない」「値がおかしい」と言われた
- 「原因を調べて」「デバッグして」と依頼された
- 「ローカルでだけ出る」「本番でだけ起きる」と言われた
- 「遅くなった？」「速くなった？」と、変更の前後の比較を求められた

## 参照ファイルの選択

| 状況 | 参照ファイル |
| --- | --- |
| CI の失敗 | `rules/ci.md` |
| アプリの挙動の不具合（表示されない、値が違う、特定の環境でだけ起きる、インストールの失敗） | `rules/app.md` |
| 変更の前後で速度や件数を比べる | `rules/measure.md` |

## 手順

### 1. 何が、どこで失敗したかを確定する

推測を始める前に、次を事実として書き出す。分からない項目は「不明」と書き、調べて埋める。

- **何が**：失敗したステップ、テスト名、画面と操作、エラーメッセージの原文
- **どこで**：コミット（SHA）、ブランチ、環境（ローカル / 検証 / 本番）、リクエスト先のホスト
- **いつから**：最後に正常だったコミットや日時。分かれば

この段階でコードを開いて原因を探さない。失敗した対象を取り違えたまま調べると、正しい推論をしても別のものを直すことになる。

### 2. 再現させる

状況に応じたファイル（上の表）を読み、手順 1 の条件で失敗を再現させる。再現しない場合は、条件のどれが違うかを先に調べる。再現しないものを直しても、直ったかどうかを確かめられない。

### 3. 範囲を絞る

再現できたら、条件を 1 つずつ変えて範囲を絞る。一度に複数の条件を変えない。どの変更が効いたのか分からなくなる。調べて**原因ではなかった**ものも控えておく。報告に載せると、同じ調査を繰り返さずに済む。

### 4. 直して、同じ方法で確かめる

原因が特定できたら修正する。修正の確認は、手順 2 で再現させたのと同じ方法で行い、失敗しなくなったことを示す。別の方法で確かめると、修正が効いたのか条件が変わったのかを区別できない。

ユーザーが調査だけを頼んだ場合は、修正せずに原因と修正案を報告する。

## 出力フォーマット

```markdown
## 失敗の内容
- 何が: <ステップ / テスト / 画面と操作>（エラーの原文: `...`）
- どこで: <コミット SHA / ブランチ / 環境 / ホスト>

## 再現
- 手順: <再現させた方法>
- 結果: 再現した / 再現しなかった（<違っていた条件>）

## 原因
- <特定した原因と根拠>（特定できていなければ「未特定」と書き、残っている候補を挙げる）

## 原因ではなかったもの
- <確かめて除外した候補と、その根拠>

## 修正と確認
- <修正内容> / <手順 2 と同じ方法で確かめた結果>（調査のみなら修正案）
```

「たぶん一時的な失敗」「環境の問題」は原因ではない。再現しない理由を特定できなければ「未特定」と書く。

## 拡張ガイド（将来の作業者向け）

新しい落とし穴を足すときは、まず既存の 3 ファイルに追記できないかを検討する。CI の読み方は `rules/ci.md`、アプリの挙動は `rules/app.md`、比較の方法は `rules/measure.md` に置く。特定のサービスやプロジェクトの構成に依存する手順は、各プロジェクトの `.claude/skills/` に置く。
