# CI の失敗を調べるとき

## その結果が今のコードのものかを確かめる

CI の結果を根拠に「落ちている」「通っている」と判断する前に、その run の head SHA が、対象ブランチの最新コミットと一致することを確かめる。

```bash
git fetch origin <ブランチ>
git rev-parse origin/<ブランチ>
gh run list --branch <ブランチ> --limit 5 --json headSha,status,conclusion,name,databaseId
```

先に fetch するのは、手元の `origin/<ブランチ>` が古いままだと、比べる相手そのものを取り違えるため。一致しない run は、古いコミットの結果である。すでに直したものを「落ちている」と報告したり、まだ走っていないものを「通った」と報告したりしないために、最初に確かめる。

## ベースブランチも落ちていないか

PR の変更を調べ始める前に、同じチェックがベースブランチの最新の run でも落ちていないかを見る。落ちていれば、その PR の変更が原因ではない。ログを読み込む前に確かめるのは、こちらの方が手間が小さく、当てはまれば調査の対象そのものが変わるため。

ベースブランチ側で直った場合も、PR の CI を再実行するだけでは反映されない。再実行は元のコミットのまま走るため、ベースブランチを PR のブランチに取り込んで、新しいコミットで CI を走らせる。

## ジョブではなく、失敗したステップと生ログから読む

ジョブ名や要約の画面から原因を推測しない。失敗したステップを特定し、そのステップの生ログを読む。

```bash
gh run view <run-id> --log-failed
# 何も出ない場合（ログの準備中、ステップが始まる前に落ちたジョブなど）
gh run view <run-id> --log --job <job-id>
```

1 つのジョブには、セットアップ、依存のインストール、ビルド、テストなど複数のステップがある。ジョブ名が「test」でも、落ちたのは依存のインストールということがある。ログは、失敗の直前の数十行だけでなく、最初にエラーや警告が出た位置までさかのぼる。後のエラーは、最初のエラーの結果であることが多い。

## 再実行は 1 回だけ、切り分けのために使う

同じコミットで 1 回だけ再実行し（`gh run rerun <run-id> --failed`）、結果を次のように扱う。

| 再実行の結果 | 判断 |
| --- | --- |
| 同じステップが同じエラーで落ちる | コードか設定の問題として調べる |
| 通る | 不安定な失敗の可能性がある。ただし原因ではないので、落ちたときのログを残し、何が不安定なのか（外部サービス、タイミング、テストの順序）を調べる |
| 別の場所で落ちる | 両方のログを読む。環境の問題が疑われる |

再実行を繰り返して通るまで待たない。通ったとしても、次の PR で同じように落ちる。

## ローカルで再現させる

CI と同じコマンドを、CI と同じバージョンでローカルで実行する。ワークフローのファイルから、実行しているコマンド、ランタイムのバージョン、環境変数を確認する。ローカルで通る場合は、違いを 1 つずつ調べる。

- ランタイムやツールのバージョン（`.nvmrc`、`setup-*` のバージョン指定）
- lockfile どおりにインストールしているか（CI は `npm ci`、ローカルは `npm install` など）
- 環境変数、タイムゾーン、ロケール
- キャッシュ（CI のキャッシュが古い依存を復元していないか）
- 並列実行やテストの実行順

## 結果を待つ

CI の完了を待つときは、短い間隔で状態を問い合わせ続けない。完了までブロックするコマンドを 1 回使う。

```bash
gh run watch <run-id> --exit-status
```
