# push する前の確認

PR のブランチを push する直前に読む。push した内容はレビュアーと CI に届くため、ここで止められるものは止める。

## push 先を確かめる

push する前に、今いるブランチと push 先を突き合わせる。

```bash
git rev-parse --abbrev-ref HEAD
git rev-parse --abbrev-ref --symbolic-full-name '@{u}'   # 追跡先（未設定ならエラーになる）
```

次のどれかに当てはまる場合は、push を実行せずに中断し、ユーザーに確認する。

- 今いるブランチが、デフォルトブランチや長命ブランチ（`main`、`develop`、`release/*` など）である
- push するコマンドの送り先（`git push origin HEAD:main` の `main` の部分）が、長命ブランチになっている
- 追跡先が、作業ブランチとは別の名前のブランチになっている（先行の PR のブランチから切ったときに起きやすい。`git push -u origin HEAD` で、作業ブランチと同じ名前の追跡先を作り直す）

長命ブランチへの直接 push は、レビューと CI を飛ばして共有の履歴を変える。取り消すには履歴の書き換えか打ち消しのコミットが必要になり、ほかの人の作業にも影響する。ブランチを切り替えた後や、別のセッションから作業を引き継いだ後は特に、思い込みで push しない。

## push 前に通すもの

プロジェクトの標準チェック（`package.json` の scripts、`AGENTS.md` / `CLAUDE.md` に書かれたコマンド）を実行し、通ってから push する。加えて、変更の種類に応じて次を実行する。

| 変更 | 追加で実行するもの | 理由 |
| --- | --- | --- |
| export の削除・移動、モジュールの分割 | ビルド | 型チェックはバンドラーの解決や動的 import の失敗を検出しない |
| 関数・コンポーネントのシグネチャの変更 | そのシグネチャを使っているテスト（呼び出し側を検索して特定する） | 変更したファイルのテストだけでは、呼び出し側の失敗が見えない |
| 依存パッケージの更新 | lockfile を含めた標準チェック一式 | 更新直後にしか原因を切り分けられない |

複数のリポジトリに同じ変更を入れる場合は、リポジトリごとにチェックを実行する。1 つで通ったことは、ほかのリポジトリで通る根拠にならない。

ビルドが作業ツリーのファイルを書き換えるプロジェクト（生成される型定義など）では、ビルド後に `git status` を見て、意図しない変更をコミットに混ぜない。

## 実行できなかったチェック

環境の制約で実行できなかったチェックは、実行したものと分けて PR 本文に書く（`write-commit` の「ローカルチェック」）。実行していないものを「確認済み」と書かない。
