# PR の分け方と、複数の PR を並べるとき

1 本の PR に何を入れるかを決めるとき、同時に複数の PR を出すとき、同じ変更を複数のリポジトリへ入れるときに読む。

## 1 本の PR に入れるもの

PR は、レビュアーが 1 つの目的として読める単位にする。作業ブランチに別種の作業（機能追加と無関係なリファクタリング、別 Issue の修正など）が混ざっていたら、作成する前に分けることをユーザーに提案する。混ざっていると、レビューで何を確かめればよいかが分からず、片方だけ差し戻すこともできない。

すでにあるブランチに別種の作業を足すように頼まれた場合も、独立してレビューできる内容なら、別ブランチを切ることを提案する。

## 同じファイルに触る PR を並行して出す

後続の PR が先行の PR と同じ行に触る場合は、後続のブランチを**先行の PR のブランチから**切り、PR のベースも先行のブランチにする。`main` などから切ると、先行がマージされるまで後続がコンフリクトしたまま止まる。

先行の PR がマージされたら、その時点で後続のブランチにベースブランチを取り込み、PR のベースがデフォルトブランチに変わっていることを確かめてから、レビューを依頼する。先行のブランチがマージ後に削除されると GitHub がベースを自動で付け替えるが、削除されない設定では付け替わらないため、手で変える。マージを待ってからまとめて対応すると、レビュー中のブランチがコンフリクトしたまま放置される。

取り込みは、ほかの人が使っているブランチではマージで行う。rebase と強制 push は、自分だけが使うブランチに限る。

## 同じ変更を複数のリポジトリへ入れる（横展開）

- 各リポジトリの PR に、ほかのリポジトリの PR へのリンクを書く。レビュアーが全体を把握できるようにするため
- **全リポジトリのレビューが出そろうまで、先行の PR をマージしない。** 後のリポジトリのレビューで方針が変わると、マージ済みのリポジトリだけ古い方針で残る
- ユーザーが作業の終点を指定した場合（「PR は作らずコミットまで」「既存ブランチへの push まで」など）は、その終点で止める。横展開は件数が多く、終点を越えた作業を取り消す手間が大きい

## 一覧から抽出した対象を扱うとき

Issue や調査結果の一覧から対象を拾って PR を分けた場合は、最後の PR を作る前に、元の一覧と作成した PR を 1 件ずつ突き合わせ、漏れが無いことを確かめる。系統ごとに分けると、どの系統にも入らなかった対象が残りやすい。
