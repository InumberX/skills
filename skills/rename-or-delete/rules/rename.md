# 改名・移動するとき

識別子・ファイル・ディレクトリ・ルートパラメータ・ラベルを改名するとき、一括置換を使うときに読む。

## 名前を決める前に確かめること

- **値の渡し先の名前**：ルートパラメータやフォームの項目名を改名するときは、その値が最終的に渡される先（API のフィールド名、スキーマ・proto の定義）を 1 つ確認してから名前を決める。入口と出口で名前が揃っていないと、変換層で取り違えが起きる
- **名前の由来**：enum や定数のラベルを変えるときは、その名前を導入した PR・Issue を検索して由来を確かめる。仕様が 1 つの対象に 2 系統の名前を与えていることがあり、片方に寄せると仕様書との対応が崩れる。由来は PR 本文に書く
- **新しい名前の空き**：新しい名前で先に検索し、既存の別の識別子・ファイル・ルートと衝突しないことを確かめる。衝突したまま一括置換すると、元からあった同名のものまで巻き込み、置換後に切り分けられなくなる

## 対象の一覧を先に合意する

ディレクトリやファイルをまとめて改名する場合は、対象の一覧を先にユーザーへ示して合意を取る。作業中に「これも規約に合わない」と気づいても、一覧に無いものは同じ変更で改名しない。別の変更として提案する。レビューする側は、合意した一覧と差分を突き合わせて確認するため。

## 置換の範囲

アプリのソース配下に限定せず、`rules/search.md` の「検索の範囲」に挙げた場所すべてを置換の対象にする。テスト・E2E シナリオ・ドキュメント・設定ファイルの旧名は、ビルドが通っても残り続け、後で壊れる。

ファイルの移動と中身の書き換えは、別のコミットに分ける。Git は移動を内容の類似度で検出するため、同じコミットで中身を大きく変えると、移動ではなく「削除と新規追加」として扱われる。そうなると、レビューで差分を追えなくなり、`git log --follow` で履歴もたどれなくなる。

## 一括置換の後に必ず目視する

`sed` やエディタの一括置換は、文字列リテラル内の一致まで書き換える。たとえばディレクトリ名を置換すると、URL のパスやリダイレクト設定の文字列まで変わり、ルーティングの判定が化ける。置換を実行したら、変更行のうち引用符を含む行だけを抜き出して全件を目視する。

```bash
git diff -U0 HEAD | grep -E '^\+[^+]' | grep -E "[\"'\`]"
```

この確認は、置換をコミットする前に行う。比較対象には `HEAD` を指定する。`git mv` や `git add` でステージ済みの変更は、`git diff` だけでは表示されず、確認から漏れるため。置換をすでにコミットした場合は、`HEAD` の代わりに置換前のコミットを指定する。`git mv` ではなく `mv` で移動したファイルは未追跡のままで、`HEAD` と比べても表示されない。先に `git add -N <移動先のパス>` で追跡対象に加えておく。YAML や Markdown のように、文字列を引用符で囲まない形式のファイルは、この抽出に掛からない。それらは変更行をすべて見る。

意図しない置換が見つかったら、その行を元に戻す。件数が多くても全件を見る。抜き取りで済ませると、見なかった行に化けが残る。

## 改名後の確認

- 旧名の全文検索が 0 件であること（名前の揺れを含めて、`rules/search.md` と同じ検索を再実行する）。意図して残すもの（変更履歴、移行ガイドなど）は、理由を付けて報告に挙げる
- typecheck・lint・テストが通ること
- export を移動したならビルドが通ること
- URL やルートを改名したなら、旧 URL へのリンク・リダイレクト・外部からの流入をどう扱うかを PR 本文に書く
