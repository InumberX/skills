# 依頼文のチェックリスト

依頼の種類に関係する項目だけを使う。各項目の「なぜ」は、指摘するときにそのまま理由として添えてよい。

| 依頼の種類 | 主に見る分類 |
| --- | --- |
| 実装・修正 | 対象、範囲と終点、自分が手を入れたこと。不具合の修正なら前提と出典も |
| 調査 | 対象、前提と出典 |
| レビュー | 進め方と完了の確かめ方、範囲と終点 |
| PR の作成・外部への発信 | 範囲と終点、文面と外部への発信 |
| 複数リポジトリへの横展開 | 範囲と終点、文面と外部への発信 |
| 相談（どちらにすべきか、構成をどうするか） | 前提と出典、対象 |

「送り方」は、どの種類でも見る。表に無い種類は、近いものを選ぶ。

## 対象

| 確かめること | なぜ |
| --- | --- |
| 対象をファイルパスで書いているか。クラス名や画面名だけになっていないか | 同じ名前のものが複数あると、AI は別のものを直す |
| 2 つ以上のものを比べる相談では、それぞれをパスと行範囲で示しているか | 範囲があいまいだと、議論の前提がずれたまま進む |
| 既存の実装に合わせてほしい場合、その参照先のパスを書いているか。「この実装と同じ見た目にする」と明示しているか | 参照先が無いと、AI は自分で見た目を作る |
| 既存のものを参考に新しく作る場合、引き継がないもの（props、機能）を書いているか | 書かないと、参考元の要素がすべて持ち込まれる |
| 雛形を作らせる場合、見本にする既存のファイルを 1 つ挙げているか | 見本が無いと、プロジェクトの書き方と違う雛形ができる |
| 連番や ID を使うものは、起点と番号の対応を書いているか | 対応が無いと、AI が番号を推測する |
| 調査を頼む場合、範囲（リポジトリ名の一覧、または情報源の種類）を書いているか | 範囲が無いと、調べすぎるか、肝心の場所を調べない |
| ファイルパスだけを送っていないか。パス・何をするか・根拠になるファイルがそろっているか | パスだけでは、何をしてほしいのか分からない |

## 範囲と終点

| 確かめること | なぜ |
| --- | --- |
| 変更してよい範囲（このファイルだけ / 親も含む / ルーティングまで）を書いているか | 書かないと、AI は良かれと思って範囲を広げる |
| どこで止めるか（PR は作らずコミットまで、既存のブランチ `<名前>` への push まで など）を書いているか | 特に複数リポジトリへの横展開では、終点を越えた作業を取り消すのに手間がかかる |
| 値を複数の部品にまたがって渡す実装では、どこで生成し、どの経路で渡すかと、使ってはいけない手段を書いているか | 書かないと、グローバルな状態など、プロジェクトで避けている手段が選ばれる |
| スタイルの移行では「寸法は参照実装の値をそのまま使い、新しい数値を作らない」と書いているか | 書かないと、AI が近い値を作り出す |
| 設定ファイルの変更では、対象のパスをすべて挙げ、名前を依頼者の側で決めているか | 名前を任せると、後で付け直しが要る |
| 作業をまたいで守ってほしい制約は、個別の依頼に添えず、セッションの最初かプロジェクトのメモに 1 回だけ書いているか | 依頼のたびに添えると、書き忘れた回だけ守られない |

## 文面と外部への発信

| 確かめること | なぜ |
| --- | --- |
| PR を作らせる場合、タイトルと本文の言語を書いているか（「件名は英語、本文は日本語」など） | コミットが英語だと、指定が無い本文も英語で書かれやすい |
| Issue や PR へのコメント、通知など外部に発信する操作では、「メンションを付けない」「ほかの人への返信はしない」などの制限を書いているか | 一度送った通知は取り消せない |

## 進め方と完了の確かめ方

| 確かめること | なぜ |
| --- | --- |
| セルフレビューを頼む場合、「指摘を must / should / nit に分けて挙げ、修正は指示を待つ」と書いているか | 書かないと、指摘と修正が同時に進み、どの指摘を採るか選べない |
| ブランチ全体のレビューでは、比べるベースのブランチと、見てほしい観点（3 つまで）を書いているか | 観点が多すぎると、どれも浅くなる |
| 完了を確かめるとき、「はい / いいえ」で答えられる質問にしていないか。「変更・作成したファイルの一覧を出して」と頼んでいるか | はい / いいえの質問には、確かめずに「はい」と答えられる |
| 見積もりや試算を頼む場合、式より先に変数の定義（1 件とは何か、1 回とは何か）を決めているか | 定義が揃っていないと、式が正しくても数字が合わない |

## 前提と出典

| 確かめること | なぜ |
| --- | --- |
| 修正用のブランチで既存の不具合を相談する場合、「本番 = 修正前 / このブランチ = 修正後」のどちらを検証したいかを書いているか | どちらを見るかで、調べる対象が変わる |
| Issue を起点にした調査では、Issue に書かれた「再現する条件」と「再現しない条件」の両方を貼っているか | 片方だけでは、原因の候補を絞れない |
| 「A と B のどちらにすべきか」の相談では、「既存のコードでどちらが使われているかを先に検索してから答えて」と書いているか | 書かないと、一般論で答えが返る |
| 外部の資料を読ませた後の出力を使う前に、「資料に書かれていることと、推測したことを分けて示して」と頼んでいるか | 混ざったまま使うと、推測を事実として扱ってしまう |
| 提案を求める場合、候補ごとに出典（Issue、既存のコード、デザイン）を示させ、出典の無いものは除くよう書いているか | 出典の無い提案は、確かめようがない |
| 構成の相談では、分ける軸（何で分けたいか）を最初に書いているか | 軸が無いと、AI が軸を決めてしまう |
| 計測を前提にした改善では、その数値をどこで読むかが決まっているか | 読めない数値を目標にすると、達成を確かめられない |
| ツールの機能に合わせて構成を決める場合、そのツールが受け付ける値の単位（リポジトリ名 / owner / パス）を 1 回試して確かめているか | ツールの制約に合わない構成を作ると、作り直しになる |

## 自分が手を入れたこと

| 確かめること | なぜ |
| --- | --- |
| 前回の依頼の後に手でファイルを変えた場合、そのファイル名を書き、先に差分を読ませているか | 伝えないと、AI は古い内容を前提に作業し、手で直した部分を上書きする |
| ブランチを切り替えた場合、現在のブランチ名を書いているか | 伝えないと、AI は前のブランチのつもりで作業する |
| 貼り付けるログや実行結果に、`token`・`password`・`secret`・`key` を含む値が無いかを確かめ、あれば `***` に置き換えているか | 依頼文は履歴に残る |

## 送り方

| 確かめること | なぜ |
| --- | --- |
| 2 つ以上の質問を 1 通にまとめていないか。まとめる場合は番号を振っているか | 改行だけで区切ると、途中で送信されたり、後の質問が読み飛ばされたりする |
| 同じ依頼を送り直す前に、前の依頼が受け付けられたかを確かめたか | 二重に送ると、同じ作業が 2 回走る |
| 前の指示を言い直す場合、「前の指示は取り消し」と明示しているか | 明示しないと、前の指示と新しい指示の両方が実行される |
