# verify-completion

「直した」「できた」と報告する前に、変更が意図どおりに働き、ほかを壊していないことを確かめるスキル。確かめた対象と方法を、報告で言える状態にする。

完了の報告が外れるのは、ほとんどが「変更した場所だけを見た」ことで起きる。共通部品のスタイルを直して、その部品を使う親の画面を開いていない。左右の要素を共通化して、片方の見た目が変わったことに気づかない。PR 本文を直して、描画すると表が崩れていた。どれも、影響しうる範囲を先に挙げれば確かめられる。

## いつ発動するか

次のいずれかに該当する場合に使う:

- 作業を終えて「完了しました」「直しました」と報告しようとしている
- 「確認して」「本当に直った？」「最終チェックして」と依頼された
- PR を出す前、デプロイの前に、変更の確認を求められた

lint・typecheck・テストで検出できるものは、それらを実行して結果に従う。本スキルは、ツールが見ない範囲（画面の見た目、描画結果、外部への影響）の確かめ方に集中する。

## 参照ファイルの選択

| 変更の種類 | 参照ファイル |
| --- | --- |
| 画面・スタイル・コンポーネント・画像 | `rules/ui.md` |
| Issue / PR の本文、ドキュメント、リンク、生成物 | `rules/content.md` |

## 手順

### 1. 影響しうる範囲を挙げる

変更した場所に加えて、次を書き出す。

- **使っている側**：変更した部品・関数・スタイルを使っている画面やモジュール（検索して特定する）
- **対になるもの**：左右、前後、開閉、ライト / ダークのように、同じ部品で作られている相手
- **条件の違い**：画面幅、ブラウザ、ログインの有無、データが空のときと多いとき

挙げた範囲が広すぎて確かめきれない場合は、どこまで確かめるかをユーザーに伝えて決める。黙って一部だけを確かめて「完了」と書かない。

### 2. 範囲ごとに確かめる方法を決めて、実行する

変更の種類に応じたファイル（上の表）を読み、確かめる方法を選んで実行する。**ログやメッセージの文言ではなく、実体を見て判定する。** 「成功しました」と表示されても、ファイル、画面、プロセス、レスポンスが実際にそうなっているかは別である。

大量の対象を一括で変える作業（画像の変換、ファイルの移行など）は、1 件だけ先に実行して結果を確かめてから、残りに進む。

### 3. 結果を 3 つに分けて報告する

確かめた結果は、次の 3 つに分けて書く。

| 区分 | 意味 |
| --- | --- |
| 確認済み | 実行して、期待どおりだった |
| 未実行 | 環境の制約などで実行できなかった。理由を添える |
| 未再現 | 実行したが、もともとの問題が手元で起きなかったため、直ったかどうかを判定できない |

「未確認」と「未再現」を混ぜない。未再現は「確かめようとしたが、確かめる前提が整わなかった」ことであり、直ったことの根拠にならない。

## 出力フォーマット

```markdown
## 確認済み
- <確かめた対象>: <方法> → <結果>

## 未実行
- <対象>: <理由>（無ければ「なし」）

## 未再現
- <対象>: <試した環境（OS・ブラウザ・画面幅など）>（無ければ「なし」）
```

PR 本文に書く場合も、同じ区分を使う。

## 拡張ガイド（将来の作業者向け）

確かめ方を足すときは、まず既存の 2 ファイルに追記できないかを検討する。画面に関わるものは `rules/ui.md`、文書・リンク・生成物は `rules/content.md` に置く。特定のプロジェクトのパスやコマンドに依存する確かめ方は、各プロジェクトの `.claude/skills/` に置く。
