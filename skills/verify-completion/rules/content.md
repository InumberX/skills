# 文書・リンク・生成物を確かめる

## Issue / PR の本文、Markdown のドキュメント

本文を書いたり直したりしたら、GitHub の描画結果で確かめる。Markdown のソースでは正しく見えても、空行の有無やインデントで、表、チェックボックス、折りたたみ（`<details>`）が崩れる。

```bash
gh api -X POST markdown -F text=@body.md -f mode=gfm > rendered.html
grep -o 'type="checkbox"' rendered.html | wc -l   # チェックボックスの数
grep -o '<table>' rendered.html | wc -l           # 表の数
grep -o '<details>' rendered.html | wc -l         # 折りたたみの数
grep -o '<h2' rendered.html | wc -l               # 見出しの数
```

`grep -c` は一致した行の数を数えるため、1 行に複数あると少なく出る。`grep -o` で一致した箇所を 1 件ずつ出してから数える。

ソースに書いた数と、描画結果の数が一致することを確かめてから完了にする。チェックボックスと見出しは、ソース側も機械的に数えられる。表と折りたたみは、ソースを見て数える。

```bash
grep -cE '^[[:space:]]*[-*] \[[ xX]\]' body.md   # ソースのチェックボックスの数
grep -c '^## ' body.md                            # ソースの見出しの数
```

ソース側の検索は、コードブロックの中の行も数える。描画結果の数と食い違ったら、まずコードブロックの中に `##` や `- [ ]` で始まる行が無いかを見る。

## PR 本文に挙動の変化を書いた

PR 本文に「並び順を変えた」「読み込みを 2 回から 1 回にした」「上限を超えても取得できる」のような挙動の変化を書いたら、その変化ごとに、**実装を元に戻すと落ちるテスト**があるかを確かめる。

本文に書いた挙動は、レビュアーにとって「この PR で保証されること」になる。テストがそれを固定していないと、後の変更で元に戻っても気づけない。テストが通っているだけでは足りない。変化を確かめていないテストは、元に戻しても通るからである。

確かめ方は、実装のファイルだけを一時的にベースブランチの内容に戻してテストを実行し、少なくとも 1 件が落ちることを見る。作業中の変更を失わないよう、先にコミットしてから行う。

```bash
git restore --source=<ベースブランチ> -- <変更した実装のファイル>  # 実装だけを元に戻す
<テストを実行するコマンド>                                          # 落ちるテストがあることを確かめる
git restore -- <変更した実装のファイル>                             # コミット済みの内容に戻す
```

テストのファイルは戻さない。テストまで戻すと、足したテスト自体が消えて、何も確かめられない。どのテストも落ちなければ、その変化を確かめるテストを足すか、本文の書き方を「テストでは固定していない」と分かる形に変える。

テストで固定しにくい変化（クエリの回数など）は、代わりに確かめられるもの（関連データが読み込まれていること、など）をテストにして、その旨を本文に書く。

## 外部へのリンク

本番で使う外部リンクを設定したら、リダイレクトの回数を確かめ、リダイレクトが 0 回になる URL に置き換える。

```bash
curl -sL -o /dev/null -w '%{http_code} %{num_redirects} %{url_effective}\n' '<URL>'
```

`-I`（HEAD リクエスト）は使わない。HEAD を受け付けずにエラーを返すサーバーがあり、実際のアクセスと結果が変わる。ステータスコードが 200 であることも合わせて確かめる。リダイレクトを挟むと表示が遅くなり、リダイレクト先が変わったときにリンク切れに気づけない。最後の `url_effective` が、最終的に表示される URL である。

## 生成物のプレビュー

メールやドキュメントなど、データから生成するもののプレビューを作るときは、表示を直す前に、プレビュー側が受け取っているデータと、本番の生成処理が受け取るデータを突き合わせ、足りないキーを列挙してから着手する。プレビュー用のデータに無い項目は、プレビューでは空のまま正しく見えてしまう。

## 静的サイトに新しいページを追加した

静的サイトジェネレーターのリポジトリにページを追加したら、コミットする前に、既存のページの先頭（front matter やレイアウトの指定）と比べる。

```bash
head -5 <既存のページ> <追加したページ>
```

front matter が無い、または書式が違うと、ジェネレーターがページとして処理せず、レイアウトが当たらないまま公開される。

## インストール・削除・設定の変更

アプリやツールのアンインストール、設定の変更は、コマンドの出力の文言ではなく、実体を見て完了を判定する。アプリ本体のファイル、常駐しているプロセス、システムの拡張機能、設定ファイルの値が、実際に期待どおりになっているかを確かめる。
