# 秘密情報の確認

export で書き出す前に、内容に秘密情報が含まれていないかを確かめる。この確認は補助的な対策であり、すべての秘密情報を検出できるわけではない。パターンに当たらなくても、秘密情報だと判断できるものは同じように扱う。

## 書かないもの

- API キー・アクセストークン・パスワード・秘密鍵
- `.env` などの環境変数ファイルに書かれた値（変数名は書いてよい）
- 接続文字列に含まれる認証情報（`postgres://user:password@host` のパスワード部分など）
- 個人情報（氏名・メールアドレス・電話番号・住所など。作業に必要な場合も、実在の値ではなく役割で書く）
- 作業の再開に必要のない社内情報

`.handoff/` は Git の管理対象外だが、ファイルとしてディスクに残り、別のエージェントにもそのまま読まれる。会話の中で一時的に扱った値でも書き出さない。

## 検出パターン

| 種類 | パターン（正規表現） |
| --- | --- |
| 秘密鍵 | `-----BEGIN [A-Z ]*PRIVATE KEY-----` |
| AWS アクセスキー | `\b(?:AKIA\|ASIA)[0-9A-Z]{16}\b` |
| GitHub トークン | `\b(?:ghp\|gho\|ghu\|ghs\|ghr)_[A-Za-z0-9]{36,}\b`、`\bgithub_pat_[A-Za-z0-9_]{22,}\b` |
| Anthropic API キー | `\bsk-ant-[A-Za-z0-9_-]{20,}` |
| OpenAI API キー | `\bsk-(?:proj-)?[A-Za-z0-9_-]{20,}` |
| Slack トークン | `\bxox[abprs]-[A-Za-z0-9-]{10,}` |
| Google API キー | `\bAIza[0-9A-Za-z_-]{35}\b` |
| JWT | `\beyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}` |
| 認証情報付きの URL | `[a-z][a-z0-9+.-]*://[^/\s:@]+:(?P<value>[^/\s@]+)@` |
| 秘密らしいキーへの代入 | キー名に `password`・`passwd`・`secret`・`token`・`api_key`・`apikey`・`private_key`・`credential` を含み（大文字小文字を区別しない）、`=` または `:` の後に値があるもの |

最後の 2 つは誤検出が多い。値がプレースホルダ（`xxx`・`<your-token>`・`${TOKEN}`・大文字の環境変数名の `$TOKEN`・`process.env.TOKEN` など）なら置き換えなくてよい。プレースホルダとみなす形は狭く保つ。`$WeePW123`（大文字と小文字が混ざる）や `<@|zy^>`（記号を含む）のように、プレースホルダに似ているだけの値は秘密情報として扱う。キー名に含まれる語が `token` だけで、値が数字だけのもの（`max_tokens: 1024`・`TOKEN_LIMIT=4096` など）はトークン数なので置き換えなくてよい。`password=12345678` のように `password`・`secret` などを含むキーでは、数字だけでも PIN やパスワードの可能性があるため置き換える。

正規表現は ASCII モード（Python の `re.ASCII`）で照合する。Unicode モードでは日本語の文字も `\w` に含まれ、「トークンはghp_...」のように日本語と隣接したトークンの前後で `\b` が境界にならず、検出できないため。

### 秘密らしいキーへの代入で、値とみなす範囲

キーへの代入では、どこまでを値とみなすかで漏れ方が変わる。少なく取ると秘密情報の残りが書き出され、多く取っても伏せすぎるだけなので、迷ったら多く取る。

- 値が引用符かバッククォートで始まるときは、対応する閉じの記号までを値とする。空白を含んでもよく、バックスラッシュでエスケープされた引用符は閉じとみなさない（`password="correct horse"` は全体を伏せる）。閉じの記号がなければ、行末までを伏せる。閉じの記号の直後に文字が続くとき（`"abc"def`）は、次の空白までを値とする。ただし、閉じの記号の後が `,`・`.`・`)`・`}` などの区切りと空白（または行末）だけなら、そこで値を終える
- 引用符で始まらない値は、次の空白（または `、`・`。`）までを値とする。途中の引用符・カンマ・括弧も値の一部として伏せる。例えば `password=it'sSecret` は `'sSecret` まで伏せる
- 末尾の `)`・`）`・バッククォートは、キーより前でまだ閉じていない開きの記号があるとき、その数だけ値の外とみなす。`)`・`）` は同じ段落、バッククォートは同じ行で数える（`f(token=x)`・`（token=x）`・`` `token=x` ``）。それ以外は値の一部として伏せる。例えば `password=Pa55word)` と `f(password=Pa55word))` は、パスワードの `)` まで伏せる
- 末尾の `:`・`.`・`!`・`?`・`,`・`;` は、プレースホルダかどうかを判断するときだけ無視する（`def f(token=None):` は `None` として扱う）。伏せるときは値に含める。ただし上の閉じの記号より後ろにあるものは値の外とする（`f(password=x).` の `.` は残す）
- 記号だけでできた値（`password=!!!!!!`）も値として伏せる
- 検出した範囲が重なったときは、両方を合わせた範囲を伏せる

表の中の `\|` は、Markdown の表を壊さないためにエスケープした `|`（どれか 1 つに一致）である。`(?P<value>...)` は、置き換える範囲を値の部分だけに絞るための名前付きグループである。

`scripts/handoff_tool.py` の `SECRET_PATTERNS` は、この表と同じ正規表現を持つ（ユニットテストで一致を確かめている）。パターンを変えるときは両方を同時に更新する。

## 見つけたときの扱い

- 値の部分だけを `[REDACTED]` に置き換える。キー名や前後の説明は残し、何が伏せられたかを引き継ぎ先が分かるようにする

  ```text
  Bad:  STRIPE_SECRET_KEY=sk_live_51H...
  Good: STRIPE_SECRET_KEY=[REDACTED]
  ```

- 置き換えた件数とセクション名をユーザーに報告する。値そのものは報告にも書かない
- ユーザーが「値も含めて」と求めても書かない。引き継ぎ先が値を必要とするなら、値の置き場所（`GITHUB_TOKEN` のような環境変数名、シークレットマネージャのキー名など）を書き、値はユーザーから直接受け取るよう `Next Actions` に書く。伏せた理由をユーザーに伝える

  ```text
  Bad:  認証には ghp_xxxxxxxx...（ユーザーの指示により値を記載）を使う
  Good: 認証には環境変数 GITHUB_TOKEN のトークンを使う（値は [REDACTED]。必要ならユーザーに確認する）
  ```

  依頼によって伏せたり伏せなかったりすると、引き継ぎファイルに秘密情報が残っているかどうかを、読む側が判断できなくなるため
- 秘密情報を含むファイルが `Changed Files` に挙がっている場合（`.env` を誤って変更したなど）は、パスは残し、Known Issues にそのファイルを確認するよう書く
